P1 - Remove the known production administrator password
-------------------------------------------------------

STATUS: RESOLVED. AdminBootstrap generates a random password when Production has
no configured password, rejects the known dev credential, and validates configured
passwords. IdentitySeeder sets MustChangePassword for generated credentials;
middleware and the web change-password page enforce the flow. Login lockout and
rate limiting are enabled. AdminBootstrapTests pass. The old acceptance criterion
rejecting an absent password is superseded by the implemented random-password flow.
Mobile onboarding still needs N05; do not reintroduce a shared production password.

Problem:
Program.cs creates the initial administrator with the fallback password
"Admin123!". That password is also published in README.md and
docker/.env.example. AuthController disables login lockout. A newly exposed
installation can be taken over before the owner changes the password.

Affected files:
- SonaFlyUI/SonaFlyUI.Server/Program.cs
- SonaFlyUI/SonaFlyUI.Server/Api/Controllers/AuthController.cs
- docker/.env.example
- README.md

Suggested fix:
1. In Production, require SonaFly:AdminDefaultPassword to be present, non-empty,
   accepted by the configured Identity password validator, and different from the
   documented development value. Refuse startup with a clear error otherwise.
2. Prefer generating a cryptographically random one-time password on first boot,
   displaying it once in local container logs, and requiring a password change at
   first login. Do not retain or document a universal credential.
3. Enable Identity lockoutOnFailure and configure a reasonable threshold and
   duration. Consider endpoint rate limiting for login and refresh requests.
4. Update deployment documentation and the environment example.

Acceptance criteria:
- A production instance cannot create an admin with Admin123! or an absent/blank
  password.

  credentials.

P1 - Invalidate sessions when account security changes
------------------------------------------------------

STATUS: PARTIAL. Security-stamp claims, JWT account checks, a hub invocation filter,
revocation on account changes, and refresh-family replay handling are implemented;
SessionInvalidationTests pass. Rotation and revocation are not atomic against each
other, however. Complete N02 before closing this security item.

Problem:
Access tokens contain identity and role claims but no security-stamp/session-version
claim. Normal JWT validation does not recheck ApplicationUser.IsEnabled. Disabling,
demoting, deleting, or resetting the password of a user therefore leaves an issued
access token valid until expiry. Password changes and resets also do not revoke the
user's existing refresh tokens.

Affected files:
- SonaFlyUI/SonaFlyUI.Server/Infrastructure/Identity/TokenService.cs
- SonaFlyUI/SonaFlyUI.Server/Program.cs
- SonaFlyUI/SonaFlyUI.Server/Api/Controllers/AuthController.cs
- SonaFlyUI/SonaFlyUI.Server/Api/Controllers/UsersController.cs
- SonaFlyUI/SonaFlyUI.Server/Domain/Entities/RefreshToken.cs

Suggested fix:
1. Put a security-stamp or explicit session-version claim in access tokens.
2. Add JwtBearer OnTokenValidated logic (or a reusable authorization validator)
   that rejects missing, deleted, disabled, or stamp-mismatched users. Cache short
   term only if database traffic becomes material.
3. Revoke all active refresh tokens for a user after password change/reset,
   disable, deletion, or other account-compromise events.
4. Decide whether a role change must immediately revoke sessions. If yes, rotate
   the security stamp and refresh-token family during the role update.
5. Detect reuse of a rotated refresh token and revoke its descendant token family.

Acceptance criteria:
- A disabled/deleted user receives 401 on the next API request and cannot use an
  existing SignalR connection for commands.
- A demoted admin immediately loses admin authorization when that is the selected
  policy.
- Old access and refresh tokens fail after password reset/change.
- Tests cover REST, SignalR, refresh rotation, token replay, and stream tickets.

N01 - P1 - Enforce playlist/mixed-tape ownership and content visibility
STATUS: RESOLVED. CollectionCaller carries the caller's identity and admin flag into
every playlist/mixed-tape service method. Reads are owner/public/system/admin and writes
owner/admin only, both as database predicates, so public never implies writable; a
collection the caller cannot see reports 404 rather than 403. Item projections and counts
are filtered by the caller's restrictions, and AddTrack validates the track against them.
CollectionAccessTests covers two users across every read/write/item/reorder route on real
SQLite and asserts the database is unchanged after each refusal.
Files: Api/Controllers/PlaylistsController.cs, MixedTapesController.cs and
Infrastructure/Services/PlaylistService.cs, MixedTapeService.cs under the server.
GetById and write methods pass only object IDs to services, with no current user
or ownership check. Any authenticated user knowing another object's ID can read
private collections or modify/delete them. Public playlist IDs are discoverable
through GetAll, so another user's public playlist can be modified immediately.
Their item projections also expose restricted tracks and AddTrack does not apply
the caller's restrictions.
Fix: Pass caller identity into service methods; enforce owner/admin write policy
and owner/public/system read policy in database predicates. Public read must not
imply public write. Filter returned items/counts by user restrictions and validate
track access before adding. Specify admin exceptions explicitly.
Acceptance: Two-user tests exercise every read/write/item/reorder route, public
read-only access, private ID access, and newly restricted existing items. Unauthorized
operations return 403/404 and never change the database.

N02 - P1 - Make refresh consumption and session revocation atomic
STATUS: RESOLVED. Refresh holds an immediate (write-lock-taking) transaction from
before the token is read until the successor commits, and claims the token with a
conditional ExecuteUpdate on RevokedUtc == null, so a caller that updates no rows gets no
descendant. The account is re-read inside the lock rather than through the token's
navigation property, so the successor and access token carry the current stamp and status.
Logout takes the same lock, so a rotation in flight has already inserted its child by the
time the family sweep runs. UpdateSecurityStampAsync's result is checked and a failure
throws instead of reporting success. RefreshRotationConcurrencyTests races independent
connections against a file-backed database; the tests were confirmed to fail against the
previous unguarded implementation.
Files: AuthController.Refresh/Logout, UserSecurityService, RefreshToken and EF mapping.
Refresh reads IsRevoked before its save without a transaction/concurrency token.
Two requests can both consume the same token and mint descendants. Worse, logout
or password reset can revoke a family/user after Refresh reads it but before it
inserts a new unrevoked descendant. The comment saying family revocation protects
in-flight rotations is not true for descendants inserted after ExecuteUpdate.
Fix: Atomically claim a still-active token and insert its successor, coordinated
with durable family/user revocation state. Use transactional compare-and-set or
an equivalent database-enforced design; do not rely only on a process-local lock.
Recheck the current account stamp/status within this protocol. Check the result of
UpdateSecurityStampAsync instead of silently assuming it succeeded.
Acceptance: Barrier-controlled tests using independent contexts/connections cover
two refreshes, refresh versus logout, password reset, disable and role change.
No successor issued from a revoked session can refresh successfully afterward.

N03 - P1 - Coordinate browser restoration/rotation and preserve transient errors
STATUS: RESOLVED. One rotation at a time, per session and across tabs: callers join
an in-flight rotation instead of starting another, and a Web Lock serialises tabs where it
is available, with the local queue as the fallback. Login and logout queue behind any
outstanding rotation. restoreSession returns null only for 400/401/403 and propagates
everything else, so an outage or 429 reaches the retry UI instead of the login page.
client.test.mjs exercises the real restoration logic (StrictMode double mount, the lock,
logout during a rotation, transient failures); AuthContext.test.tsx covers the retry path.
Files: web src/api/client.ts (restoreSession), auth/AuthContext.tsx, src/main.tsx.
restoreSession bypasses pendingRefresh; StrictMode runs the mount effect twice in
development and two tabs also share the same rotating cookie. Both can send the
same token, triggering the new replay-family revocation. An epoch check cannot
prevent a Set-Cookie response from modifying the browser's cookie. restoreSession
also catches all failures as null, turning a network/503/429 outage into a login
redirect instead of the advertised retryable session error. Existing AuthContext
tests mock restoreSession and therefore miss this path.
Fix: Share one restoration/refresh operation per session and coordinate across
tabs (or design server rotation to safely accommodate legitimate concurrent use).
Serialize logout/login with outstanding cookie mutations. Return null only for
definitively absent/invalid sessions; propagate transient failures to retry UI.
Acceptance: StrictMode mount, two tabs, logout during delayed refresh, login replacing
an old session, and network/503/429 tests using the real client restoration logic.
Normal reloads must not revoke a healthy session; stale responses must not restore it.

N04 - P1 - Protect the last-admin invariant across concurrent requests
STATUS: RESOLVED. Disable, Delete and role changes run inside
SerializedWrites.BeginExclusiveAsync, which takes SQLite's write lock before the guard
query, and the user is loaded inside that scope. Only a success status commits. A caller
that loses the lock beyond its timeout gets 409 rather than 500.
UserAdministrationConcurrencyTests races independent connections on a file-backed database
across disable/disable, demote/demote and delete/demote; the tests were confirmed to fail
against the previous implementation.
File: server Api/Controllers/UsersController.cs.
IsLastEnabledAdminAsync runs before Update's transaction; Disable/Delete have no
transaction around the check and mutation. Two admins can concurrently disable
each other, or concurrent demotions can each observe two enabled admins and both
succeed. Self-disable protection does not prevent this.
Fix: Put the count check and mutation in one serialized database operation covering
all disable/delete/demotion paths. Use a locking/isolation strategy appropriate for
SQLite and handle retry/conflict results. Preserve role allowlisting and rollback.
